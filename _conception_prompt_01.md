# 004. Механизмы надежности
## 4.1. Гарантированная доставка (Reliability)
- **Pull-модель**: Станции сами забирают задачи из своих персональных очередей в RabbitMQ.
- **Local Persistence**: После получения задачи станция сохраняет её в локальную БД SQLite.
- **Immediate ACK**: Подтверждение (ACK) отправляется в RabbitMQ сразу после записи в SQLite. Это освобождает очередь и гарантирует, что задача не потеряется при перезагрузке станции.

<a id="ttl-dlx"></a>
## 4.2. Жизненный цикл и протухание (TTL & DLX)
Спутники имеют строгое «окно видимости». Если станция была офлайн:
* Каждое сообщение имеет TTL (Time-To-Live), равный времени окончания пролета.
* ~~При истечении TTL сообщение попадает в Dead Letter Exchange (DLX), оттуда автоматом в DLQ (queue).~~ - отказались пока от этого механизма, кажется лишним.
* ~~Серверный воркер вычитывает сообщения из DLX и помечает наблюдение в PostgreSQL как SKIPPED.~~
* При истечении TTL сообщение удаляется из очереди - RabbitMQ сам умеет удалять сообщения по TTL (заголовок `expiration`, в миллисекундах), если не указывать `x-dead-letter-exchange`, делает это автоматически, но всегда из головы очереди, последовательно, пока не дойдёт до "живого" сообщения.
* Серверный воркер   scheduler-задача будет регулярно запрашивать БД-таблицу `observations` на предмет только что истёкшего периода `observations.end_time`. Каждое FUTURE-наблюдение без актуальных загрузок в telemetries, images будет помечено `status='FAILED'`

+ [ниже: Протухание наблюдений](#ttl-ob9s)

## 4.3. Обновление параметров (Update TLE)
- При обновлении TLE сервер отправляет новое сообщение с тем же observation_id и повышенной версией (updated_at).
- Клиент выполняет Upsert в SQLite, актуализируя параметры запланированного наблюдения.

# 005. Сценарий загрузки данных (Data Ingestion)
По ходу наблюдения за спутником станция получает от него поток данных, который пишет в файлы телеметрии, изображения. Потом генерирует изображение с визуализацией сигнала - Waterfall, и audio-файл.
Для минимизации нагрузки на API-сервер используется метод прямой заливки (upload) файлов в облачное хранилище:
- **Request**: Клиент запрашивает у API разрешение на загрузку.
- **Authorize**: API генерирует S3 Presigned URL с коротким TTL (т.е. ссылка может использоваться несколько раз, но с ограничением по времени).
- **Upload**: Клиент загружает файлы (Images, Telemetry, Waterfall) напрямую в S3.
- **Finalize**: Клиент отправляет отчет в API со списком успешно загруженных путей. Сервер обновляет метаданные в БД. 
    * возможны ситуации с потерей связи станцией, тогда в S3 остаются файлы, но API не знает об этом - при "оживании" коннекта станции, она повторит загрузку файла с тем же именем/путём/ключом, и в случае успеха отчитается в API
    * - вроде со стороны S3 могут генерироваться events, которые будут отслеживаться в сервере API? пока не понятно, см. ниже
    * **Уточнение claude.ai** «S3 сам может отправить уведомление в RabbitMQ»: MinIO поддерживает bucket notifications через AMQP (RabbitMQ), но это требует отдельной настройки на уровне MinIO и не является стандартным поведением. AWS S3 Event Notifications работают через SNS/SQS, не через RabbitMQ напрямую.
     **Риск:** если использоваться будет и MinIO (dev), и AWS/Yandex (prod) — механика уведомлений будет разной. Это усложняет поддержку.


## Сценарий получения Presigned Upload URL

**Зачем**: Чтобы клиент не знал секретных ключей (Access/Secret Key) от S3.
**Как**: FastAPI использует boto3 (или aioboto3), генерирует временную ссылку (например, PUT запрос к bucket/station1/file.raw?signature=...) и отдает её клиенту.
  https://yandex.cloud/ru/docs/storage/operations/objects/link-for-upload

**Безопасность**: 
  TTL ссылки должен быть коротким (например, 15–30 минут), достаточным для загрузки файла.

  Запрещаем генерацию предподписанных s3-URL'ов (а следовательно и заливку файлов в S3), если истёк разрешённый период заливки данных по наблюдению - по дефолту 30 дней от времени окончания наблюдения.

  Удалённые станции-клиенты могут подолгу оставаться в оффлайне, например, ожидая ремонта.
    После восстановления попытаются долить оставшиеся файлы.
    Не позволяем в автоматическом режиме пополнять сколь угодно старые наблюдения.

## Регистрация результатов в БД
Загрузка в S3 -> Вызов API для записи в БД информации о загруженных файлах.

**Риск**: Если клиент загрузил файл в S3, но в этот момент пропал интернет и он не успел дернуть API, файл в S3 станет "сиротой" (orphan file) — он там есть, но БД о нем не знает.

**Решение**: Покуда клиент не получил ответа от API "файл зарегистрирован", при следующем прогоне задачи повторной отправки файла, он запросит presigned URL с тем же именем файла - API сгенерирует идентичный s3_key (с иерархией папок, включающей observation_id и start_time, см. ниже). Повторная отправка файла в s3 идемпотентна, даже если файл уже существует, это не является ошибкой. После успешной повторной отправки в s3, клиент отчитается об этом в API `POST /api/v2/observations/{id}/files` 

**Не принятые варианты**: 
1. Использовать S3 Event Notifications (если S3 поддерживает это, например MinIO или AWS). 
   S3 сам может отправить уведомление в RabbitMQ, когда файл полностью загружен, 
   тогда серверный воркер подберет это событие и обновит БД.
2. Если это слишком сложно, клиент должен присылать в API не просто "список путей", а полный отчет о завершении миссии, включая контрольные суммы (checksum) файлов.


**Структура ключей в S3 (обратная совместимость с v1)**

Структура S3-ключей сохраняется из Soniks v1 для обеспечения обратной совместимости с накопленной БД:

```
data_obs/{year}/{month}/{day}/{hour}/{observation_id}/{filename}
```

Примеры по типам файлов:
- **demoddata**: `data_obs/2026/6/1/19/1369597/data_1369597_2026-06-01T19-30-36_g0`
- **image**: `data_obs/2026/6/2/11/1370554/data_1370554_2026-06-02T11-46-32.png`
- **waterfall**: `data_obs/2026/6/2/6/1370658/waterfall_1370658_2026-06-02T06-40-08.png`
- **audio**: `data_obs/2026/6/2/6/1370658/audio_1370658_2026-06-02T06-40-08.ogg`
  Базовый URL хранилища: `https://storage.yandexcloud.net/sonics-data-prod/`

Дата в v1-пути (`year/month/day/hour`) берётся из `observation.start_time` — не из времени фактической заливки файла. Это позволяет корректно группировать файлы даже при отложенной заливке после восстановления связи.
Однако в v2 у нас появились таблицы статистики, в которых группировка и агрегация производится по дате из `observation.end_time`. 
См. пример в https://sonik.space/observations/1488459/ - после 00:00 имена файлов переходят с 26 на 27-е июля, а директория остаётся "вчерашней": `2026/07/26/23`

Хочется в v2 избегать рассогласованностей, особенно в ключах, поэтому, может быть, стоит in FUTURE собирать v2-пути (`year/month/day/hour`) на основе `observation.end_time` 

> **Примечание:** дубликаты с одинаковым именем не допускаются. Имя файла формируется на стороне клиента (клиент знает `observation_id`, `start_time`, `end_time`, timestamp кадра).

**Idempotency при повторной заливке**
 
- Presigned URL выдаётся повторно для того же `s3_key` до тех пор, пока не истечёт expiration time наблюдения (по умолчанию +30 дней от end_time). Это покрывает сценарий потери связи после PUT в S3.
- После успешной регистрации файла через `POST .../files` повторный запрос presigned URL для того же `s3_key` по-прежнему разрешён, защиты от перезаписи файла в s3 нет.

**Security - Авторизация записи файлов** 
Право станции на регистрацию файлов по наблюдению подтверждается на стороне API через `ObservationORM.hash_api_key` vs. `authorization: token ...` - чтобы скомпрометированная станция не могла абьюзить API редактированием / порчей чужих наблюдений, сервис проверяет соответствие `observation_id`, `station_id` и `station_api_token`.

# 005.003 Регистрация файлов наблюдения (`POST /files`)

`POST /api/v2/observations/{observation_id}/files` — шаг "Finalize" сценария загрузки данных ([005](#005-сценарий-загрузки-данных-data-ingestion)). Принимает список уже загруженных в S3 файлов, обновляет метаданные в PostgreSQL.

**Контракт запроса** — список объектов `{ s3_key, file_type }`, где `file_type ∈ {demoddata, image, waterfall, audio}` (номенклатура сохранена из v1). Явного поля даты/времени кадра нет — `timestamp` для `demoddata`/`image` парсится из `s3_key` по той же схеме, что в v1 (`{prefix}_{observation_id}_{timestamp}[_suffix].{ext}`), сознательно, а не через отдельное поле запроса — иначе придётся разрешать конфликт между полем и именем файла, что не обосновано отдельной задачей.

**Авторизация** — тот же механизм, что и для `presigned-urls` ([005](#сценарий-получения-presigned-upload-url)): `CachedStationObservationContextProvider`, заголовок `Authorization: Token ...`, включая тот же 30-дневный guard на приём файлов по истёкшим наблюдениям.

**checksum сознательно не запрашивается** — API не верифицирует содержимое S3 (тяжёлый трафик вынесен "наружу", вне процессов backend-приложения).

**Идемпотентность — поэлементная**, не "всё или ничего":
- `demoddata`/`image` — уникальность по `s3_key` на уровне БД (constraint), повторная регистрация того же ключа — `already_exists` (не ошибка), другого — обычная новая запись.
- `waterfall`/`audio` — единственное поле на самой записи наблюдения (не отдельная таблица). Совпадающий `s3_key` — молчаливый no-op (`already_exists`). Отличающийся от уже сохранённого — отклоняется (`rejected`), перезапись через API не допускается; исправление — только через админку.

Ответ API — по каждому файлу из списка отдельно (`registered` / `already_exists` / `rejected`), чтобы станция могла безопасно повторить неполный batch после обрыва связи, не потеряв уже принятые файлы.

**Побочные эффекты одного вызова** (в одной транзакции, под блокировкой строки `observations`):
1. Если `observation.status == 'Future'` и в батче есть ≥1 успешно зарегистрированный файл (любого `file_type`) — единожды: `observation.status → 'Unknown'`, `future_count -= 1`, `unknown_count += 1` (таблицы статистики станции/спутника/пользователя, см. [005.004](#005004-таблицы-статистики)), `last_observation_at`/`last_active_at` подтягиваются вперёд до `observation.end_time`.

2. пока в рамках задачи SONIKS-373 (отправка файлов client'ом в s3 и добавление недостающих для этого api-методов) не инкрементируем статистику по полученным пакетам - лучше это делать консолидированно, собирая агрегат после завершения обработки потока файлов, чтобы не заваливать pg очень многочисленными, хоть и короткими, `select for update`. Только меняем статус future -> unknown при поступлении первой пачки. Подсчет и инкремент статистики принятых пакетов по итогу наблюдения будет формулироваться в отдельной задаче
3. `observations_count` этим эндпоинтом не трогаются (?) 
4. `decoded_packets_count` — результат отдельного, последующего процесса декодирования телеметрии; `observations_count` инкрементируется при создании наблюдения (см. таблицу переходов в разделе [006](#006-статусная-модель-observation-state-machine)).


# 005.004 Таблицы статистики

Семь таблиц (`infrastructure/postgres/models/statistics/`), обновляемых при регистрации файлов ([005.003](#005003-регистрация-файлов-наблюдения-post-files)) и других переходах статуса ([006](#006-статусная-модель-observation-state-machine)):

| Таблица | Ключ | Гранулярность | Статус-брейкдаун |
| :--- | :--- | :--- | :--- |
| `station_observation_stats` | `station_id` | за всё время | да |
| `station_observation_daily_stats` | `station_id + date` | по дням | да |
| `station_satellites_daily_stats` | `station_id + satellite_uuid + date` | по дням | нет — только `observations_count`, `packets_count` |
| `satellite_observation_stats` | `satellite_uuid` | за всё время | да |
| `satellite_observation_daily_stats` | `satellite_uuid + date` | по дням | да |
| `observer_users_stats` | `satellite_uuid + observer_user_uuid` | за всё время, без даты | нет — только `observations_count`, `packets_count`, `last_active_at` |
| `user_observation_daily_stats` | `user_uuid + date` | по дням | да |

Накопительной таблицы "пользователь за всё время по всем спутникам" — сознательно нет, только `observer_users_stats` (пара со спутником) и `user_observation_daily_stats` (по дням). При необходимости — агрегируется запросом, не денормализуется отдельной таблицей.

`observer_user_uuid` = `observations.author_uuid`. Наблюдения с `author_uuid IS NULL` в пользовательскую статистику не попадают.

**Дата-ключ daily-таблиц — `observation.end_time::date`**, не дата фактического поступления отчёта и не `start_time`. Согласовано с решением по схеме S3-путей ([005](#структура-ключей-в-s3-обратная-совместимость-с-v1)) — оба места используют одно и то же поле как источник даты, чтобы не создавать новых источников рассогласования. Историческая порция путей/данных (сформированная по `start_time`) не мигрируется и не участвует активно в текущих процессах.


# 006. Статусная модель Observation (State Machine)
Для удобства обсуждения предлагается концептуальная статусная модель для точного отслеживания жизненного цикла наблюдения на стороне сервера и распределенных станций.
В коде и моделях эти статусы не реализованы (и не будут! - пока не имеют отображения во фронтенд), используем эту модель только для рассуждений о ЖЦ и непротиворечивом выявлении скрытых требований.

| Статус           | Описание                                                 | Инициатор          | Условие перехода                                              |
|:-----------------|:---------------------------------------------------------|:-------------------|:--------------------------------------------------------------|
| **PENDING**      | Создана запись в БД API, ждет отправки в брокер.         | Server (API/Logic) | Начальное состояние при планировании.                         |
| **SENT**         | Задача упакована и отправлена в RabbitMQ.                | Server (Taskiq)    | Успешная публикация сообщения в очередь станции.              |
| **PLANNED**      | Доставлено и сохранено в локальную SQLite станции.       | Client (RPi) + API | Станция сделала `ACK` в MQ и вызвала API-метод подтверждения. |
| **UPDATED**      | Требуется повторная отправка из-за смены TLE/параметров. | Server (API)       | Изменение исходных данных спутника в БД сервера.              |
| **CANCELLING**   | В брокер отправлена команда на удаление из плана.        | Server (API)       | Запрос пользователя на отмену наблюдения.                     |
| **CANCELLED**    | Станция подтвердила удаление задачи из локальной БД.     | Client (RPi)       | Вызов API-метода станцией после обработки команды отмены.     |
| **UNDELIVERED**  | Станция не прочитала задачу (TTL в MQ истек).            | Server (DLX)       | Срабатывание Dead Letter Exchange в RabbitMQ.                 |
| **SKIPPED**      | Окно наблюдения прошло, но отчета от станции нет.        | Server (Worker)    | Проверка по таймеру (если статус не стал REPORTED).           |
| ~~**REPORTED**~~ | ~~Станция успешно отчиталась о завершении.~~ не будем    | ~~Client (RPi)~~   | ~~Вызов API-метода финализации (загрузка метаданных).~~       |

## Диаграмма переходов
```mermaid
stateDiagram-v2
    [*] --> PENDING: Запись в БД API
    
    PENDING --> SENT: Сервер отправил в RabbitMQ
    
    SENT --> PLANNED: Станция сохранила в SQLite подтвердила ACK-уведомлением о прочтении (или через API)
    SENT --> UNDELIVERED: TTL истек (обработка DLX)
    
    PLANNED --> UPDATED: Параметры TLE изменились
    UPDATED --> SENT: Повторная отправка в MQ
    
    PLANNED --> CANCELLING: Запрос на отмену
    CANCELLING --> CANCELLED: Станция удалила из плана
    
    PLANNED --> REPORTED: Успешный прием и Upload
    PLANNED --> SKIPPED: Окно прошло (нет отчета)
    PLANNED --> FAILED: Станция отчиталась об ошибке
    
    REPORTED --> [*]
    UNDELIVERED --> [*]
    CANCELLED --> [*]
    SKIPPED --> [*]
    FAILED --> [*]
```
### Ключевые особенности модели:
**Разделение UNDELIVERED и SKIPPED:**
* UNDELIVERED — это технический статус (проблема связи/инфраструктуры).
* SKIPPED — это логический статус (станция онлайн, но по какой-то причине не смогла инициировать процесс вовремя).

**Управление отменой (CANCELLING):**
Мы не просто удаляем запись в БД, а переводим её в CANCELLING, пока станция не подтвердит, что она выкинула задачу из своего расписания. Это предотвращает ситуацию, когда станция начинает "фантомное" наблюдение, которое сервер уже не ждет.

Если станция офлайн, когда команда отмены публикуется в очередь, TTL на команду отмены = TTL наблюдения, либо серверный воркер должен переводить CANCELLING → CANCELLED принудительно после окончания окна наблюдения.



**Цикл обновления (UPDATED):**
Статус UPDATED служит триггером для повторной отправки сообщения в брокер. Новое сообщение должно иметь тот же observation_id, чтобы клиент выполнил REPLACE или UPDATE в своей SQLite.

Обновление TLE допустимо только если `now < observation_start_time - delta`. Нужно ввести понятие «замороженного» наблюдения, которое нельзя обновлять после определённого порога

### Реализованная статусная модель
```python
class ObservationStatusEnum(StrEnum):
    """Статус наблюдения (для API и web-интерфейса)."""

    FUTURE = "Future"
    FAILED = "Failed"
    BAD = "Bad"
    GOOD = "Good"
    UNKNOWN = "Unknown"
```
При получении файлов ("пакетов данных") от клиента-станции в первый раз, наблюдение должно поменять статус с "Future" на "Unknown". Реализовано в `POST /api/v2/observations/{id}/files` — см. [005.003](#005003-регистрация-файлов-наблюдения-post-files).

При дальнейших сменах статуса счётчики статистики так же требуют обновления — таблицы статистики хранят **снапшот** текущего распределения наблюдений по статусам (`future/failed/bad/good/unknown_count`), а не количество "было когда-либо в этом статусе". Поэтому каждый переход статуса — это всегда **пара** операций: decrement счётчика старого статуса и increment счётчика нового, в одной транзакции. Эталон итогового состояния — ETL-пересчёт `s11_stats.py` (миграция статистики из prod v1), финальные цифры инкрементальной логики обязаны совпадать с результатом его повторного запуска.

Распределение ответственности за переходы статуса между эндпоинтами (уточнено в рамках проектирования `POST /files`):

| Переход | `future_count` | `unknown_count` | `bad_count` / `good_count` | `failed_count` | Инициатор |
| :--- | :--- | :--- | :--- | :--- | :--- |
| создание наблюдения → `Future` | `+1` | — | — | — | эндпоинт(-ы) планирования наблюдения (`POST /stations/{id}/observations`, `POST /satellites/{uuid}/observations`) — вне рамок данного документа |
| `Future` → `Unknown` | `-1` | `+1` | — | — | `POST /observations/{id}/files`, один раз, при первой успешно зарегистрированной пачке файлов |
| `Unknown` → `Bad`/`Good` | — | `-1` | `+1` | — | эндпоинт "оценка наблюдения/водопада" — вне рамок данного документа |
| `Future` → `Failed` | `-1` | — | — | `+1` | фоновый воркер протухания, **только после 30-дневного периода охлаждения** от `observation.end_time` (совпадает с окном разрешённой заливки файлов — см. [005](#005-сценарий-загрузки-данных-data-ingestion)) |

Симметрия `Future → Failed` и 30-дневного guard на выдачу presigned URL/регистрацию файлов не случайна: пока наблюдение может получить данные (окно не истекло), воркер не переводит его в `Failed`; как только окно истекло и воркер перевёл наблюдение в `Failed`, `POST /files` для этого наблюдения уже отклоняется тем же 30-дневным guard'ом (раздел 005) — поэтому обратный переход `Failed → Unknown` от опоздавших файлов **структурно невозможен**, отдельная обработка этого случая не требуется.

Статус Failed будет назначаться автоматически фоновым воркером, если данных не поступало в течение 30 дней после окончания окна наблюдения (см. таблицу выше).

# 007. Политика публикации задач (On-Demand Generation)
Сервер придерживается стратегии «ленивой» публикации для оптимизации ресурсов брокера и актуальности данных.
- **Условие публикации**: Задачи-наблюдения не создаются и не публикуются автоматически для всех станций подряд.
- **Инициация**: Генерация пачки наблюдений происходит только по явному запросу к API:
    * `POST /api/v2/stations/{id}/observations` — планирование для конкретной станции (станция должна быть отмечена статусом ONLINE).
    * `POST /api/v2/satellites/{uuid}/observations` — планирование пролетов конкретного спутника по всей сети доступных станций.
- **Преимущество**: Это гарантирует, что в очереди RabbitMQ попадают только актуальные на момент запроса данные (TLE, частоты), и снижает количество "мертвых" сообщений в DLQ для оффлайн-объектов.

- **Настройка TTL**: Время жизни сообщения в очереди RabbitMQ должно рассчитываться динамически для каждого пролета спутника (Tend−Tstart+buffer) / связанного с ним наблюдения - задание на наблюдение теряет актуальность, если спутник уже улетел за пределы видимости.
- Сообщения с истёкшим TTL [лежат в очереди](https://www.rabbitmq.com/docs/ttl#message-ttl-applied-retroactively), пока к ней не подключится клиент/потребитель. Когда в процессе вычитывания очереди в голову подходит сообщение с истёкшим TTL, RabbitMQ автоматически помещает его в DLX->DLQ, не доставляя клиенту, переходит к следующему сообщению. 

- **Именование очередей**: Для каждой станции удобно использовать паттерн station.{id}.tasks, чтобы DLX мог возвращать метаданные о том, откуда "прилетело" протухшее сообщение. DLX должен получать `routing key` со `station_id` через заголовки (x-dead-letter-routing-key)

109. Orphan-файлы в S3: два разных сценария, требуют разного решения

Тема удаления файлов-сирот в S3 (объект загружен, но в БД не зарегистрирован) не была явно спроектирована в разделах 005/005.003. При разборе кейса выявлено два принципиально разных по механике обнаружения сценария — фиксируем оба, чтобы не потерять из виду.

**109.1. Orphan из-за `rejected` (waterfall/audio с расходящимся `s3_key`)**

Станция залила альтернативный waterfall/audio (другой timestamp/имя), вызвала `POST /files`, получила `rejected` — раздел 005.003, «Идемпотентность — поэлементная». В момент ответа API уже знает точный `s3_key` файла-сироты — он присутствует в текущем запросе.

Решение (согласовано, к реализации): синхронное удаление объекта (`delete_object`) внутри обработчика `POST /files`, сразу после вынесения вердикта `rejected`, тем же S3-клиентом, что используется для генерации presigned URL в `PUT /presigned-urls` — операция с метаданными объекта, не требует чтения содержимого, не противоречит принципу «API не верифицирует содержимое S3» (005.003).

Демоддата/image под это решение не подпадают — там `rejected`-статуса не существует в принципе (уникальность по `s3_key` на уровне БД constraint, дубликат стабильно уходит в `already_exists`, а не в конфликт).

**109.2. Orphan из-за полного обрыва связи (файл залит в S3, `POST /files` не вызван вообще)**

Отличается от 109.1 тем, что API не имеет никакой информации об этом файле — ни один эндпоинт не получает `s3_key` такого файла, пока станция не восстановит связь и не попробует его зарегистрировать сама (штатный сценарий idempotent-заливки, раздел 005, «Idempotency при повторной заливке»).

Обнаружение возможно только сверкой: листинг S3 по префиксам `data_obs/{year}/{month}/{day}/{hour}/{observation_id}/` против реестра `s3_key` в БД. Это отдельный процесс (воркер), не описанный ни в одном из существующих разделов — не смешивать с логикой протухания наблюдений (раздел 006, `Future → Failed`), это разные по природе процессы: протухание работает с наблюдениями по `end_time`, а сверка orphan-файлов — с объектами бакета по факту их существования.

Статус: не спроектировано, приоритет не определён. Требует отдельной задачи (окно поиска, частота сверки, согласование с 30-дневным guard на приём файлов из раздела 005 — файл, найденный в бакете в пределах guard-окна, не может считаться orphan, т.к. станция ещё вправе его зарегистрировать).

**Связь с реализацией 109.1**

Как только модули из запроса будут получены и логика синхронного удаления при `rejected` реализована — код `POST /files` должен получить docstring/комментарий, явно отмечающий:
- что синхронное удаление покрывает только сценарий 109.1;
- что сценарий 109.2 сознательно не покрывается этим же кодом и требует отдельного процесса сверки, если/когда будет спроектирован.

**109.3. Orphan-помойка от скомпрометированного клиента**

Клиент только запрашивает presigned-url'ы, заливает по ним файлы в S3, но не отчитывается по ним в /files.
  - похоже на "потерял связь / выключился надолго", но с абьюзом на "скрытие" файлов - просто использует наше облако в качестве файлопомойки, ведёт свой реестр, невозбранно имеет к ним бесконечный доступ на чтение.

    В следующих итерация проекта: нужно удалять файлы, не зарегистрированные в нашем реестре /files по истечению тех же 30 дней. **Как?**

        variant 1. Регистрировать в БД обращения к API presigned-urls, по истечению 30 дней удалять не использованные (отложенной taskiq-задачей)
        variant 2. Выставлять по дефолту время жизни файла в S3 на 30 дней, потом переключать на бессрочное хранение в рамках регистрации API /files. И, напротив, удалять не зарегистрнированные отложенной задачей.

  - **Банить таких клиентов**: деавторизация, комментарий-предупреждение в БД-запись для админов/модераторов.
